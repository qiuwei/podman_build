# podman for Ubuntu 22.04 (jammy), built from source

GitHub Actions builds podman and conmon from upstream source tags inside a real
Ubuntu 22.04 environment, packages them as `.deb`s, and publishes them as a
signed apt repository on GitHub Pages.

**Published repo:** `https://<owner>.github.io/podman_build`

## Why this exists

Ubuntu 22.04 ships podman **3.4.4** and has never rebased it. There is no
backport and no usable PPA:

| Source | jammy podman | Status |
| --- | --- | --- |
| `jammy/universe` | 3.4.4 | four years old |
| `jammy-backports` | *nothing* | contains only `cockpit-podman` |
| `ppa:projectatomic/ppa` | 1.6.2 | abandoned in 2019 |
| Launchpad "Podman Packaging Team" | *nothing* | owns zero PPAs |
| OBS `home:/alvistack` | 6.1.2 | third-party, amd64-only, huge lib blast radius |
| OBS `devel:/kubic:.../unstable` | 4.6.2 | third-party, frozen since 2023 |

So we build our own.

## Why podman 4.9.3 specifically

This is the newest podman that can be built *natively* on jammy, and the newest
one whose runtime dependencies jammy can actually satisfy. Three constraints
converge:

1. **Go version.** jammy's newest Go is `1.18`. podman 5.8.x and 6.1.x both
   declare `go 1.26.0` in `go.mod`; only the 4.x series declares `go 1.18`.
2. **Network backend.** jammy has no `netavark`/`aardvark-dns` packages. podman
   **4.9.3 is the last release with CNI backend support** — podman 5.0 removed
   it. We pin `network_backend = "cni"`, using jammy's
   `containernetworking-plugins`.
3. **Config packages.** jammy's `golang-github-containers-common` is `0.44.4`
   (podman 3.x era) while podman 4.9.3 wants `>= 0.57.4`. We therefore vendor
   `containers.conf`, `registries.conf` and `policy.json` ourselves.

Pushing past 4.9.3 means shipping a newer Go toolchain and building against
glibc 2.35 in a combination upstream does not test, plus rebuilding the network
stack. Not worth it for this fleet.

## Using the repository

Install the signing key and source list, then pin the repo so it cannot drag in
unrelated upgrades:

```bash
sudo mkdir -p /etc/apt/keyrings
curl -fsSL https://<owner>.github.io/podman_build/podman.asc \
  | sudo tee /etc/apt/keyrings/podman.asc >/dev/null

echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/podman.asc] \
https://<owner>.github.io/podman_build jammy stable" \
  | sudo tee /etc/apt/sources.list.d/podman.list

# Keep this repo scoped to the container tooling. Without this, anything it
# happens to publish could win a version comparison against a distro package.
sudo tee /etc/apt/preferences.d/podman.pref >/dev/null <<'EOF'
Package: *
Pin: origin <owner>.github.io
Pin-Priority: 100

Package: podman podman-docker conmon
Pin: origin <owner>.github.io
Pin-Priority: 990
EOF

sudo apt update
apt-cache policy podman    # expect 4.9.3 from the Pages origin
sudo apt install podman
```

The repo root also contains a `podman.list` template generated by the publishing
step, with a ready-made line per distribution and component.

### Upgrading from the distro package

The packages `Replaces:` their distro counterparts. Removing podman 3.4.4 drops
its images and containers unless you migrate the store first:

```bash
sudo podman ps -a          # note what exists
podman system migrate      # or just accept a fresh store
sudo apt install podman
```

## Packages produced

| Package | Contents |
| --- | --- |
| `podman` | `podman`, `podman-remote`, libexec helpers, systemd units, man pages, shell completions, vendored container configs |
| `podman-docker` | optional `/usr/bin/docker` shim; conflicts with a real Docker install |
| `conmon` | built from source — see below |

### Why we ship our own conmon

jammy's conmon is **2.0.25** (2021), four years older than podman 4.9.3.
podman 4.x drives conmon considerably harder than podman 3.4.4 did, and that
pairing is untested by upstream and by every distro. The `podman` package
depends on `conmon (>= 2.1.0)`, which apt cannot satisfy from jammy — so ours is
always selected, structurally rather than by pinning.

## Building locally

Requires docker or podman:

```bash
make deb      # -> ./out/*.deb
make shell    # drop into the jammy build container to poke at things
```

Or drive the scripts directly inside any jammy environment:

```bash
scripts/00-build-deps.sh     # apt deps (root)
scripts/10-build-conmon.sh   # -> /build/stage-conmon
scripts/20-build-podman.sh   # -> /build/stage-podman
scripts/30-make-debs.sh      # -> /build/out/*.deb
```

`30-make-debs.sh` finishes by running `objdump` over the built `podman` binary
and failing if it links any shared library not covered by the package's
`Depends:`. That check exists because the dependency list in
`packaging/podman/control.in` is derived by hand from the pinned `BUILDTAGS` in
`scripts/20-build-podman.sh`, and the two can drift.

## Bumping versions

`podman` and `conmon` versions are workflow inputs:

```bash
gh workflow run build-apt-repo.yml -f podman_version=4.9.4
```

To rebuild the *same* upstream version after a packaging change, bump
`deb_revision` — the resulting version (`4.9.3-2~jammy1`) sorts above
`4.9.3-1~jammy1`, so apt sees it as an upgrade.

Going to podman 5.x/6.x is not a version bump, it is a project: it needs a
newer Go toolchain, a `netavark`+`aardvark-dns` build, and probably moving the
whole thing to a noble base.

## Known caveats

- **Only the newest build is retained.** The publishing step replaces the repo
  snapshot each run, so superseded versions disappear. Pin exact versions on
  hosts that must hold one.
- **`ubuntu-22.04` runners are on GitHub's retirement path.** When they go, the
  build keeps working as-is: it already runs in an `ubuntu:22.04` container on a
  newer runner. Only the local `docker/Dockerfile` needs the same treatment,
  which it already has.
- **The third-party publishing action is a small dependency.**
  `jinnatar/actions-aptly-repo` was last updated in October 2024. Consider
  pinning it to a commit SHA, as kanidm does, rather than tracking `@v2`.
- **The OCI runtime is jammy's.** jammy ships crun 0.17 (2021) and runc 1.1.0
  (2022), both older than podman 4.9.3 itself. We do not pin `runtime` in
  `containers.conf`, so podman picks crun. **If containers fail to start, the
  OCI runtime is the first thing to suspect** — set `runtime = "runc"` in
  `/etc/containers/containers.conf.d/` and retest. Building a modern crun is the
  natural next increment if that turns out to matter.
- **GPG signing needs secrets.** Without `GPG_PRIVATE_KEY` and `GPG_PASSPHRASE`
  set on the repository, the published repo is **unsigned** and apt will refuse
  it. The action only signs when the key is present.

## Repository layout

```
scripts/           build steps, run in order inside a jammy container
  00-build-deps.sh   apt dependencies
  10-build-conmon.sh conmon from source
  20-build-podman.sh podman from source
  30-make-debs.sh    assemble .debs + verify declared dependencies
packaging/
  configs/           vendored containers.conf / registries.conf / policy.json
  podman/            control template
  podman-docker/     control template
  conmon/            control template
docker/Dockerfile    jammy build environment
Makefile             local convenience wrapper
.github/workflows/   build + publish pipeline
```
